## 二、P0 详情

### A1 GET 接口没有统一异常兜底

**位置**：`server.py` `do_GET()`（3350-3401）→ `_handle_api_get()`（3604-3970）。所有 `if path == "/api/xxx": self._api_xxx(q); return` 都没有 `try`。

对比：`do_POST()` 的每个分支都包了 `try/except` 并回 `{"ok": false, "error": ...}`，GET 侧完全没有。

**触发条件**（任一即可）：

- `user_data.json` 里某个账号的 `nickname` 是 `null`（外部脚本或手工编辑产生）：`load_user_data()` 第 2424-2426 行会把它写进 `list_index`，随后 `_api_authors` 的 `sort_key` 返回 `(None, "x")`，与 `("abc", "y")` 比较抛 `TypeError`；
- `user_data.json` 里某个账号的值不是 dict（例如字符串）：`_load_user_data_locked` 第 2414 行 `for k in old` 对 int/None 抛 `TypeError`；
- `data.json` 里某个 `works` 元素是 `null`：`/api/meta`（4015 行）与 `/api/authors?year=`（4086 行）
  都写的是 `w.get("date")`，对 `None` 抛 `AttributeError`；
- 任何磁盘/编码类 `OSError`（`json` 已在内部捕获，但 `os.path`、`open` 之外的调用没有）。

**影响**：异常穿透到 `socketserver`，连接被直接关闭、响应为空。前端 `resp.json()` 抛
`SyntaxError`，只显示「列表加载失败，稍后再试」——**真实原因只出现在服务端控制台**。
用户侧表现为「某个筛选一选就空白」「服务时好时坏」，极难自查。

**建议**：

```python
def do_GET(self):
    if not self._client_ok():
        return
    try:
        self._dispatch_get()
    except (BrokenPipeError, ConnectionResetError):
        pass
    except Exception as e:
        traceback.print_exc()          # 控制台留全栈，便于排查
        try:
            self._send_json({"ok": False, "error": "%s: %s" % (type(e).__name__, e)}, 500)
        except Exception:
            pass
```

同时把 `_api_authors` 的 `sort_key` 改成 `(x.get("nickname") or "")`，
`_load_user_data_locked` 的清理循环加 `isinstance(old, dict)` 判断。

### A2 删除作品：跨盘复制 + 全程持锁

**位置**：`_recycle_put()`（744-760）用 `shutil.move(full, dst)`；`_works_delete_inner()`（807-891）
整个「搬文件 → 改内存 → 写 data.json」都在 `with _CACHE_LOCK:` 内。

**触发条件**：正常删除任何作品。`recycle-bin/` 在项目盘（通常 D:），媒体在 `E:\...`，
**一定跨卷**，`shutil.move` 退化成 `copy2 + unlink`。

**影响**：

1. 删 15 GB 的一批作品 = 真复制 15 GB，期间 `_CACHE_LOCK` 被独占，
   而 `load_data()` / `load_user_data()` / `/api/authors` 都要这把锁 → **整个网页在这几分钟内全部转圈**（含轮询 `/api/rescan_status`）；
2. 复制中途断电/被杀进程 → 回收站里留半份、原件因为 unlink 未执行而仍在，但**记录已经写了一半**（见 B1），状态不一致；
3. 磁盘瞬时占用翻倍，E 盘大的时候容易把系统盘写满。

**建议**：把「搬文件」移出 `_CACHE_LOCK`（先搬、再持锁改索引，`_recycle_restore` 已经是这种写法），
并在 `_recycle_put` 里先判断是否跨卷（`os.stat(src).st_dev != os.stat(dst_dir).st_dev`），
跨卷时给前端一个「正在复制 N GB，请勿关闭」的进度，或改成「先标记、后台搬」。

### A3 回收站批次 ID 会碰撞，恢复时误删另一批

**位置**：`server.py:798`

```python
batch_id = time.strftime("%Y%m%d-%H%M%S") + "-" + (uid[-6:] or "0")
```

**触发条件**：对**同一个 uid** 在**同一秒内**执行两次删除（前端多选、连续点击、脚本批量调用都可能）。
两次记录都写进 `回收站.json`，但 `recycle-bin/<batch_id>/` 是同一个目录
（`_recycle_put` 遇到同名文件会加 `_1` 后缀，所以两批文件混在一起）。

**影响**：恢复第一批时，`_recycle_restore()` 先按 id 过滤记录——
`d["batches"] = [x for x in ... if x.get("id") != batch_id]`（1108 行）会把**两条同 id 的记录一起删掉**，
接着 `shutil.rmtree(bdir)`（1111 行）把**第二批仍在回收站里的文件一起物理删除**。
结果：第二批文件没了、记录也没了，界面里连「恢复失败」都看不到，只有磁盘上少了一堆文件。
这是不可撤销的。

**建议**：批次 ID 加随机后缀（`uuid4().hex[:6]`）或毫秒 + 自增；`_recycle_put` 在批次目录已存在且
`回收站.json` 里已有同 id 时直接换 id。恢复末尾的 `rmtree` 改成「只删空目录」（`os.rmdir`），
非空就保留并提示。

### A4 桥接服务：CORS 全开 + POST 无保护

**位置**：`bridge.py:747-751`（`Access-Control-Allow-Origin: *`，注释写「允许任意来源没关系」）、
`831-880`（`_queue_add`）、`882-909`（`do_POST` 无 `try`）。

**触发条件与影响**（两条独立风险）：

1. **任意网页可以调用**。绑定 `127.0.0.1` 只挡了外网，挡不住浏览器里打开的任意站点：
   恶意页面可 `fetch('http://127.0.0.1:8790/lookup?nickname=...')` **读取**用户的作者库
   （昵称、抖音号、作品数、状态、标签都返回），也可 `POST /queue/add` **写入**队列；
   更严重的是 `_queue_add` 在「库里没有这个人」时会调 `admin_create_author(sec_uid)`
   （第 857 行），进而请求 8723 的 `/api/create_author` —— 这是**用桥接服务当代理往本地库塞作者**，
   会真实写 `user_data.json` 并触网。`POST /queue/clear` 还能一键清空待下载区。
2. **一条畸形请求就能断连**。`item = {..."follower": int(body.get("follower") or 0)...}`
   （843 行）：`{"uid":"1","follower":"abc"}` → `ValueError` → 未捕获 → 连接关闭，客户端拿不到任何 JSON；
   `tags` 传成字符串时会被逐字符拆成标签数组。

**建议**：

- CORS 收紧成只允许扩展来源（`chrome-extension://<id>`）或干脆不发 CORS 头，
  靠扩展的 `host_permissions` 直连；
- 加 `_client_ok()` 同款校验（Host 必须是 `127.0.0.1:8790`）；
- `do_POST` 外层包 `try/except` 统一回 JSON；
- `_queue_add` 的数值字段用 `try: int(...) except: 0`，字符串字段先 `isinstance(x, str)` 再截断。

## 三、P1 详情

### B1 回收站记录写盘失败被吞掉

`_recycle_save()`（733-741）捕获 `OSError` 只 `print`，不返回状态。调用点（901-913）在**文件已经搬进
`recycle-bin/` 之后**调用它。一旦 `回收站.json` 写失败（磁盘满、被占用、权限），文件就在回收站目录里
但记录没了：界面上看不到这批，既不能恢复也不能彻底删除，只能自己去翻 `recycle-bin/` 目录。

**建议**：`_recycle_save` 返回 `bool`；失败时把批次目录里的文件原路搬回（或至少把 `batch_id` 打到
`删除记录.jsonl` 并回一个显式错误，让用户知道「文件在 recycle-bin/<id>/ 里」）。

### B2 `LIKE` 前缀匹配未转义（已复现）

`download_db.py:138-139`、`164-165`：

```python
"UPDATE file SET folder=?, rel=? || substr(rel, ?) WHERE rel LIKE ?"
... (pre + "%",)
```

`pre` 是作者文件夹名 + `/`。Windows 允许文件夹名含 `%`，而 `LIKE` 里 `%` 是通配符。

实测（内存 SQLite）：

```
文件夹名含 %  → UPDATE 命中 2 行（预期 1 行）：
  UID1_100%_发布作品/a.mp4      → 被改
  UID1_100off_发布作品/b.mp4    → 被误改
```

（注：`_` 我单独测过，同构文件名不会误匹配，主要风险在 `%`。）

**影响**：改名的同时会把另一个作者文件夹的记录前缀改掉 → 「文件数」虚高/丢失、「多久没下载过」算错，
bridge 卡片上的「本地已存 N」跟着错。

**建议**：`WHERE substr(rel, 1, ?) = ?`（传 `len(pre)` 和 `pre`），或 `LIKE ? ESCAPE '\'` 并对
`\`、`%`、`_` 转义。

### B3 `_recycle_batch_dir` 不做校验

```python
def _recycle_batch_dir(batch_id):
    """批次目录（只接受记录里存在的 id，杜绝传 ../.. 穿越）。"""
    return os.path.join(RECYCLE_DIR, batch_id)      # 没有任何校验
```

注释承诺的事没做。当前所有调用点确实先查了 `回收站.json`，所以**现在不可远程触发**；
但只要 `data/回收站.json` 被别的脚本/用户改出一个 `"id": "../../.."`，`purge` / `restore` 末尾的
`shutil.rmtree` 就会删到项目外。属于纵深防御缺失。

**建议**：加一行 `if not re.fullmatch(r"[0-9]{8}-[0-9]{6}-[0-9A-Za-z]{1,12}", batch_id): return ""`，
调用点判空即拒。

### B4 folder_merge 可能出现半合并

`_precheck_conflicts()` 只把每个 child 与 **main** 比对。若两个 child 之间有同名但内容不同的文件：
预检通过 → 第一个 child 的文件搬进 main → 第二个 child 的文件在 `_merge_files` 里 `_same_content` 失败 →
记 `conflict`、`blocked = True`，但**第一个已经搬完了**（`os.rmdir` 会跳过，所以目录还在，但内容少了一半）。
这正是模块头部承诺「部分合并比不合并更难收拾」要避免的情形。

**建议**：预检改成「所有目录两两比对」（child 之间也要比），或先算全量 `(name → [size, md5])` 再判断。

### B5 标注合并假设值都是 dict

`server.py:2409-2416`：

```python
for uid, old in (CACHE.get("user_applied") or {}).items():
    ...
    for k in old:            # old 可能是 str / int / None
        if k not in cur: acc.pop(k, None)
```

`old` 来自上一轮 `user_data.json` 的 `accounts[uid]`。若某条是 `null` 或数字（外部脚本写入、
手工编辑出错），`for k in None` 抛 `TypeError`，整个 `load_user_data()` 失败 → 该请求空响应（见 A1）。

另外 2461 行 `CACHE["user_applied"] = new_acc` 直接把磁盘 JSON 的 dict 挂进缓存，
而 2420 行 `acc.update(ua)` 之后 `CACHE["accounts"][uid]` 与 `user_applied[uid]` 共享同一批内层对象，
后续任何就地修改都会「污染上一轮快照」，让「删字段」的比较基准失真。

**建议**：循环前 `if not isinstance(old, dict): continue`；`user_applied` 存一份浅拷贝
`{u: dict(v) for u, v in new_acc.items() if isinstance(v, dict)}`。

### B6 删除部分失败仍改索引

`_works_delete_inner` 819-861：单个文件 `OSError` 只进 `failed[]`，但作品仍然从 `works` 里删掉、
`work_count` 照样减。结果是**磁盘上还有文件、界面里已经没了**（下次重扫又冒出来，作品数忽多忽少）。

**建议**：作品粒度判定——某个作品的文件有任一失败，就把这个作品留在 `works` 里（只删成功的文件），
返回里明确列出「N 个作品因文件被占用未能删除」。

### B7 bridge `_read_json` 超限不读 body

```python
if n <= 0 or n > limit:
    return {}            # 没有 self.rfile.read(n)，也没有 Connection: close
```

`protocol_version = "HTTP/1.1"` 且 `_json()` 都带 `Content-Length`，连接会被复用；
超限请求残留的 body 会被当成下一个请求的请求行解析，后续响应全部错乱（表现为随机 400 或挂起）。

**建议**：超限时 `self.close_connection = True` 并读完丢弃，或直接回 413。

## 四、P2 详情（要点）

- **C1**：`paths.py:58` 与 `start-browser.bat:6` 各写死一份 `...\.workbuddy\binaries\python\versions\3.13.12\python.exe`。
  `start-all.bat` 有 `if not exist "%PY%" set "PY=python"` 兜底，`start-browser.bat` **没有**——
  路径失效时直接 `[ERROR] Python not found` 退出。建议 bat 里也加兜底，或统一读 `paths.py`。
- **C2**：`_instance_alive()` 判据是响应前 200 字节里有 `"total_authors"`。`/api/meta` 的 JSON 目前把它排在前面，
  但任何人调换 key 顺序就会误判「没有实例在跑」→ 起第二个实例 → 端口冲突。
  建议改用 `/api/meta` 返回里的固定版本字段做精确判断。
- **C3**：`scanner.main()` 的 `changed` 不含「`uid_to_sec` 有新映射」，纯 sec_uid 更新时 `data.json` 不重写
  （内存里改了，磁盘没改）。建议把 `uid_to_sec` 变化也计入 `changed`。
- **C4**：`merge_accounts()` 用 `(date, desc)` 去重，而 `scan_author_folder()` 是按 `aweme_id` 聚合的。
  跨文件夹合并时，同一天同描述的两条不同作品会丢一条（文件不再出现在索引里，但不影响磁盘）。
- **C5**：`offset` 传负值会走 Python 负切片（`result[-10:-10+60]`），`limit` 无上限（`?limit=1000000` 会构造巨大列表）。
  建议 `offset = max(0, min(offset, total))`、`limit = max(1, min(limit, 2000))`。
- **C6**：`_safe_subdir` / `_files_dup_delete` 用 `abspath(...).startswith(root + sep)` 判越界。
  目录里有 junction/symlink 指向外部时会被判为「在内部」。本地单用户风险低，但和 `safe_media_path`
  用 `realpath` 的口径不一致，建议统一。
- **C7**：`_send_file` 把整文件读进内存再发（`fp.read()`）。当前只服务 html/js/css/缩略图/封面，都小；
  但 `STATIC_FILES` 里若将来加了大文件会直接吃掉内存。建议改成 64KB 分块写。
- **C8**：`folder_merge._md5(path, limit=None)` 的 `limit` 从未被使用；`PROJECT.md`（126 / 318 行）仍在说
  `scanner.py` 有 `--incremental` 死参数，实际代码里连解析都没有（**是文档过时，不是代码冗余**）；
  `_recycle_load` 的 docstring 写 `data/recycle-bin.json`，实际是 `data/回收站.json`。
